# R1-3b — MuseScore 4.7.5 导出探针（MusicXML → MIDI 的 CC64）

- 日期：2026-10-07　执行环境：`.venv-research`（Python 3.14.6，pin 见 `requirements-research.txt`）
- 渲染器：`D:\MuseScore 4\bin\MuseScore4.exe` → `MuseScore4 4.7.5`，exit 0
- 工具：`tools/musescore_export_probe.py`
- 样本：20 首含印刷 `<pedal>` 的乐谱 + 2 首无 pedal 的负对照
- 原始证据：`evidence/R1/R1-3b-20/`（不加 `-f`）、`evidence/R1/R1-3b-force/`（加 `-f`）

## 结果

| 指标 | 不加 `-f` | 加 `-f` |
|:--|--:|--:|
| 导出成功（MIDI 存在且可解析） | 16 / 20 | **20 / 20** |
| 失败（exit 1320，无 MIDI） | 4 / 20 | **0 / 20** |
| 负对照 0 条 CC64 | 2 / 2 | 2 / 2 |
| 恒等式 `CC64 == 2×min(start,stop)` | 14 / 16 | **16 / 20** |
| 字面 `CC64/元素数 ≥ 0.8` | 9 / 16 | 11 / 20 |
| **真否决**（`start > 0` 却 0 条 CC64） | 0 / 16 | **0 / 20** |

关键交叉验证：`Chopin/Ballades/1` 加 `-f` 后 = **432** 条 CC64，与计划书 §附录A 记录的 `465 → 432（0.929）` **完全一致**；`Chopin/Ballades/3` = 478，同样与记录一致。

## 两类必须区分的现象

1. **exit 1320（4/20，仅出现在不加 `-f` 时）**：stdout/stderr 为空、不生成 MIDI。加 `-f` 后 4/4 全部成功 → 与计划书 §12 风险 13 / §11.2 B-a 描述一致，**处置已明确：导出统一加 `-f`**。
2. **exit 0xC0000005 ACCESS_VIOLATION（1 例：`Bach/Fugue/bwv_846`）**：进程非零退出，但 **MIDI 正常生成且可解析**（该曲无 pedal，0 条 CC64 属正确）。加/不加 `-f` 均复现。计划书 §10.2 只记录了"exit 1320 且无产物"的情形，本例是**新形态**：非零退出 + 有效产物。按计划书纪律：**记录，不猜测原因**。

## 结论与后果

- **导出链路成立**：20/20 成功、负对照正确、**0 次真否决**——G0 的导出条件在本仓库独立复现通过。
- **"成功"的判定不能只看 exit code**：必须用"产物存在且可解析"，exit code 仅作记录（否则 `bwv_846` 会被误判为失败）。
- **字面判据（`CC64/元素数 ≈ 1.0`）在本样本上会误报 9/20**：样本中 14/20 结构不平衡（`start != stop`），而计划书 §1.1 明确"孤立 stop 是合法 UP，不是缺陷"。该字面判据与计划书自身的实际统计口径冲突。
